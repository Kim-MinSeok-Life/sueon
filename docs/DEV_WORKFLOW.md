# SUEO:N 개발 환경·브랜치 운영 및 작업 인계 지침

> 파일 위치: `docs/DEV_WORKFLOW.md`  
> 적용 대상: **노트북 로컬 Claude Code 세션과 Claude Code 클라우드 세션 모두**  
> 목적: 로컬 전용 자료를 보호하면서, 두 환경에서 개발한 코드·의사결정·검증 결과를 안전하게 연결한다.

## 1. 프로젝트 및 문서 적용 원칙

- 프로젝트 공식 서비스명은 **SUEO:N(수어온)**이다. 파일 및 폴더 이름에는 `SUEON` 또는 `sueon`을 사용한다.
- **이 문서는 개발 환경 간 협업 방식에 관한 공통 운영 지침**이다. 시스템 아키텍처, 수어 데이터 처리, 기존 구현을 독단적으로 재설계하라는 지시가 아니다.
- 기존 프로젝트에 `CLAUDE.md`, `AGENTS.md`, 다른 개발 규칙과 기술 설계 문서가 있으면 먼저 확인한다. 충돌하는 지침이 발견되면 **자의적으로 덮어쓰지 말고 충돌 내용을 보고**한다.
- 실제 프로젝트의 브랜치 구성·Git 원격 설정·테스트 명령·코드 상태는 매 작업 시 확인한다. 이 문서에 있는 예시를 실제 저장소의 확정된 상태로 간주하지 않는다.
- 작업의 사실관계는 **실제 소스코드, Git 커밋/차이, 테스트 출력**을 기준으로 검증한다. AI가 작성한 인계 문서만으로 구현 성공을 판단하지 않는다.

## 2. 각 환경의 역할

| 구분 | 노트북 로컬 Claude Code | Claude Code 클라우드 세션 |
|---|---|---|
| 기본 역할 | **주 개발·실행·통합 검증·최종 병합** | **이동 중 보조 개발·가능한 범위의 자체 검증·인계** |
| 주 사용 기기 | Windows 노트북(예: IntelliJ 터미널) | 휴대폰; 필요한 경우 PC 웹에서도 같은 클라우드 세션 사용 |
| 주 작업 브랜치 | `tester1` | `tester1_cloud`를 작업 시작 기준으로 사용 |
| 파일 접근 | 로컬 작업 폴더 및 허용된 로컬 전용 자료 | 클라우드에 제공된 저장소/파일만 접근 가능 |
| 완료 기준 | 실제 코드·환경·화면 검증 후 통합 | 변경사항과 한계·테스트 결과를 기록하고 원격에 전달 |
| `main` 병합 | **로컬 검증 후에만 진행** | 직접 수행하지 않음 |

- 기기가 아니라 **실행 환경**에 따라 역할을 구분한다. 클라우드 세션은 같은 계정 권한 범위 내에서 PC 웹과 휴대폰으로 이어서 열 수 있다.
- 로컬 터미널 세션과 클라우드 세션의 **대화 기록은 자동으로 합쳐지지 않는다**. 세션 간 코드 및 작업 맥락의 전달 경로는 Git과 인계 문서다.
- PC가 종료되거나 절전 중이어도 클라우드 개발은 가능하지만, **노트북 로컬 실행 환경에 접속하거나 로컬 전용 파일을 자동으로 읽는 것은 아니다**.

## 3. 브랜치 구성과 책임

- `main`: 검증 완료된 최종 통합 브랜치. 클라우드에서 직접 수정/병합 금지.
- `tester1`: 로컬 주 개발 브랜치. 개발, 최종 검증 및 `main` 반영의 기준.
- `tester1_cloud`: 클라우드 작업의 **기준·통합 브랜치**. 로컬에서 검증되지 않은 변경은 이 브랜치에만 두거나, 작업별 브랜치에 분리해 둔다.
- `claude/...` 등 작업별 브랜치: **클라우드 도구가 필요에 따라 만드는 실제 Git 브랜치**. 자동 생성 여부 및 푸시/PR 방식은 실제 Claude Code 기능과 설정을 확인한다. 무조건 생성된다고 가정하거나 고정된 이름을 전제하지 않는다.
- `review-cloud` 등 임시 검증 브랜치: 로컬에서 변경사항을 안전하게 확인하기 위해 필요할 때만 사용한다.

> `tester1_cloud`는 별도 원격 저장소가 아니라 **같은 GitHub 저장소의 브랜치**다. 작업별 브랜치도 원격으로 푸시한 경우에는 GitHub 브랜치 수에 포함된다. 오래된 작업 브랜치는 반영 여부를 확인한 뒤 정리할 수 있다.

## 4. 표준 작업 순서

### A. 최초 시작: 반드시 로컬에서

1. **현재 공개 버전을 보존**한다. 가능한 경우 해당 커밋을 태그로 표시하거나 별도 백업을 확보한다. 보존 작업 중 기존 파일을 삭제/덮어쓰지 않는다.
2. 노트북에서 현재 브랜치·커밋·미커밋 변경사항·원격 설정을 확인한다.
3. 로컬 **`tester1`에서 개발과 필요한 테스트를 수행**한다.
4. 검증된 변경을 커밋하고 `origin/tester1`로 푸시한다.
5. 최초에 `tester1_cloud`가 없다면 **최신 `tester1` 커밋을 기준으로 생성하여 푸시**한다. 두 브랜치가 같은 커밋에서 출발하므로 이 최초 준비 단계 자체에서 브랜치 차이로 인한 충돌은 없다.
6. 이후 클라우드 환경에서 SUEO:N GitHub 저장소의 `tester1_cloud`를 작업의 **시작 기준(base)**으로 선택했는지 확인한다.

### B. 로컬 → 클라우드: 이동 전

1. 로컬에서 가능한 작업을 마무리하고 `git status`를 확인한다.
2. 클라우드에 필요한 **추적 대상 코드만** 커밋하고 `tester1`을 푸시한다. 로컬 전용 자료·비밀정보는 절대 함께 추가하지 않는다.
3. **기존 클라우드 작업 중 미반영 변경사항이 있는지** 확인한다.
4. 미반영 변경사항이 없다면 `tester1_cloud`를 최신 `tester1`과 동기화한다. 변경사항이 있다면 먼저 비교·병합하여 보존한 뒤 동기화한다.
5. 클라우드에서 작업할 기능과 완료 조건을 좁게 정의한다. 동시 작업 중인 팀원 파일이나 핵심 구조를 불필요하게 수정하지 않는다.

**주의:** 동기화란 기존 `tester1_cloud` 기록을 강제로 덮어쓰라는 뜻이 아니다. 무심코 `git push --force`, `git reset --hard`를 실행하지 않는다. 이미 분기된 두 브랜치는 변경사항을 확인하고 적절히 병합한다.

### C. 클라우드: 휴대폰 개발 중

1. GitHub에 올라온 `tester1_cloud` 상태를 기준으로 작업한다.
2. Claude Code 클라우드가 작업별 브랜치를 자동으로 만드는 경우, **자동 생성된 브랜치를 그대로 활용**하고 `tester1_cloud`에 반영하는 과정은 별도로 확인한다. 작업별 브랜치를 지원하지 않거나 다른 방식으로 동작하면 실제 기능에 맞게 진행한다.
3. 한 번에 **독립적이고 범위가 작은 작업**을 수행한다. 예: UI 문구·스타일 개선, 제한된 기능 수정, 정적 검사, 관련 문서 정리.
4. 가능한 테스트를 실행하되, **미실행·실패·환경상 불가능**을 명확히 구분한다.
5. 3D 아바타 실제 동작, 수어 표현의 정확성, VRM 관절·손목·몸 관통, 모바일 시각적 결과, 실제 음성 입출력 등은 **클라우드 테스트만으로 검증 완료라고 선언하지 않는다**.
6. 작업을 끝낼 때 아래 인계 문서를 갱신하고 **코드 변경과 함께 커밋**한다.
7. 작업 결과를 GitHub 원격 브랜치에 푸시한다. 클라우드가 별도 작업 브랜치에 푸시했다면 **PR의 대상 브랜치를 `tester1_cloud`로 설정**하고, 실제 반영 여부를 확인한다. 임의로 `tester1`이나 `main`에 병합하지 않는다.

### D. 클라우드 → 로컬: 노트북 복귀 후

1. 노트북에서 `git status`로 미커밋 변경사항을 확인하고, 필요하면 안전하게 커밋/보존한 뒤 진행한다.
2. `git fetch origin`으로 GitHub의 최신 원격 이력을 가져온다. **현재 작업 브랜치와 파일은 이 단계에서 자동 변경되지 않는다.**
3. `tester1`과 `origin/tester1_cloud`의 커밋 및 파일 차이를 검토한다. 클라우드 변경이 작업별 브랜치에만 있다면 해당 브랜치/PR을 먼저 확인한다.
4. 필요하면 **별도 검증 브랜치**를 만들어 클라우드 변경을 실행하고 테스트한다. 이때 노트북 로컬 전용 자료와 설정이 필요한 검증은 반드시 로컬에서 수행한다.
5. 인계 문서의 주장과 실제 코드·Git 기록·테스트 결과를 대조한다. 이상이 있으면 병합 전에 수정한다.
6. 검증된 변경사항만 `tester1`에 병합한다. 충돌이 발생하면 해결한 뒤 다시 테스트한다.
7. 병합 완료된 `tester1`을 푸시하고, **다음 클라우드 작업에 앞서** `tester1_cloud`가 최신 `tester1`을 포함하도록 동기화한다.
8. `main`은 최종 로컬 검증과 팀 합의가 완료된 시점에만 병합한다.

## 5. `fetch`와 `pull`의 구분

- `git fetch origin`: 원격 저장소의 최신 **커밋·브랜치 정보**를 내려받는다. 현재 체크아웃한 브랜치와 작업 트리를 자동 병합하지 않는다. **검토 전 단계에 권장**.
- `git pull`: 일반적으로 `fetch` 후 현재 브랜치에 **병합 또는 리베이스**를 시도한다. 설정과 상태에 따라 충돌·실패·작업 파일 변경이 발생할 수 있다.
- 따라서 클라우드에서 돌아온 직후 무조건 `pull`부터 하지 않는다. **`fetch` → 차이 확인 → 로컬 검증 → 명시적 병합** 순서로 작업한다.

**참고 명령(예시, 저장소 상태 확인 후 사용):**

```bash
# 로컬에서 현재 상태 확인
git status
git branch -vv

# 원격 정보만 갱신
git fetch origin

# tester1 기준으로 클라우드에 추가된 커밋/파일 변경 확인
git log --oneline tester1..origin/tester1_cloud
git diff tester1 origin/tester1_cloud

# 필요시, 현재 미커밋 변경이 없는 상태에서 검증용 브랜치 생성
git switch -c review-cloud origin/tester1_cloud

# 검증 후 tester1으로 돌아와 병합(충돌 시 확인 및 해결)
git switch tester1
git merge review-cloud
```

> 위 명령은 **실행 예시일 뿐 자동 실행 지시가 아니다.** `tester1_cloud`가 아직 없거나, 로컬 변경사항이 미커밋 상태라면 그대로 실행하지 않는다. `git diff`는 기준 커밋 차이이며 실제 병합 후 최종 결과와 항상 동일한 것은 아니다.

## 6. 공통 인계 문서 작성 규칙

**권장 경로:** `docs/cloud-handoff.md`  
**작성 주체:** 클라우드 Claude Code  
**소비·검증 주체:** 로컬 Claude Code

- 최초 파일이 없다면 만든다. 이미 있다면 **동일 파일을 갱신**한다. 매 작업마다 새로운 문서를 무분별하게 생성하지 않는다.
- 매번 최신 작업의 결과를 맨 위에 기록하고, 중요한 과거 결정·실패 시도·미해결 이력은 보존한다. 길어질 경우 일정한 분량으로 요약하되 원래의 커밋/PR 참조는 남긴다.
- **문서 갱신 자체도 커밋·푸시 대상**이다. 최신 코드와 인계 문서가 같은 Git 변경 이력으로 연결되어야 한다.
- 완료했다고 쓰려면 **실제 실행 근거**가 있어야 한다. 검증하지 않은 기능은 '미검증'으로 명시한다.
- 비밀번호, API 키, 토큰, 개인 데이터, 로컬 전용 자료의 원문 또는 경로상 민감정보를 기록하지 않는다.

### 인계 문서에 필요한 필수 항목

1. **작업 식별 정보:** 날짜, 세션/작업명, 기준 브랜치, 시작 커밋 SHA, 완료 브랜치, 최종 커밋 SHA, 관련 PR
2. **작업 목표 및 범위:** 요청받은 변경과 제외한 영역
3. **실제 변경 파일:** 경로별 수정 내용, 추가·삭제 여부
4. **구현 내용:** 핵심 변경 및 기존 구조와의 연동 방식
5. **기술적 판단:** 선택 이유, 중요한 대안·제약
6. **검증 결과:** 실행 명령, 성공/실패, 오류 및 **실제로 수행하지 못한 테스트**
7. **미해결 문제·주의사항:** 오류, 제한, 예상되는 영향
8. **로컬 확인 과제:** 로컬 자료가 있어야만 가능한 테스트, 모바일·VRM·수어 정확성 확인 항목
9. **다음 단계:** 로컬 세션이 먼저 확인할 사항과 안전한 병합 방식

## 7. 로컬 전용 자료·보안 원칙

- `.env`, API 키, 토큰, 허가되지 않은 데이터셋, 개인정보, 비공개 자료는 GitHub/인계 문서에 올리지 않는다.
- `.gitignore`를 사용하더라도 **이미 추적 중인 파일에는 자동 적용되지 않음**을 유의한다. 커밋 직전 `git status`와 `git diff --cached`로 실제 포함 파일을 확인한다.
- 로컬에서 Claude Code를 실행하면 **Claude가 읽도록 제공된 로컬 파일 내용이 모델 서비스로 전송될 수 있다.** 'GitHub에 푸시하지 않았다'는 것만으로 외부 전송이 차단되는 것은 아니다.
- 로컬 자료를 클라우드에 전달하거나 클라우드 실행 명령으로 로컬 저장소를 묶어 업로드하기 전에 **전송 범위와 권한**을 확인한다. 특히 로컬 전용 자료가 있는 폴더에서 자동 업로드 기능을 무심코 사용하지 않는다.
- 계정 권한과 공유 방식은 소속 조직 및 서비스 공급자 정책을 따른다. 서로 다른 팀원의 개발 내용이 같은 세션에 섞이지 않도록 관리한다.

## 8. 로컬·클라우드 Claude Code에 공통으로 지시할 행동

> 이 저장소에서는 `docs/DEV_WORKFLOW.md`에 따라 작업한다. **현재 실행 환경이 로컬인지 클라우드인지 먼저 확인하고**, 해당 환경의 역할을 지킨다.
>
> 작업 전: 기존 `CLAUDE.md` 등 규칙, Git 상태, 기준 브랜치, 변경 이력을 확인한다.  
> 작업 중: 기존 구조를 존중하고 요청 범위에서만 수정하며, 중요한 결정과 검증 근거를 기록한다.  
> 클라우드 작업 종료 전: 코드와 `docs/cloud-handoff.md`를 갱신·커밋·푸시하고, 로컬 검증이 필요한 항목을 분명히 남긴다.  
> 로컬 복귀 시: 원격을 `fetch`해 차이를 검토하고, 인계 문서를 실제 코드와 대조한 뒤 검증된 변경만 `tester1`에 병합한다.  
> **클라우드에서는 `main` 및 `tester1`에 임의로 직접 병합하지 않는다.** 위험한 강제 푸시·리셋·대규모 삭제를 수행하지 않는다.

## 9. 운영 상태 및 예외

- **확정된 운영 원칙:** 최초 작업은 로컬 `tester1`에서 시작한다. 클라우드는 `tester1_cloud` 기준으로 보조 개발한다. 로컬에서 최종 검증 후 `tester1` 및 `main`에 반영한다.
- **환경에 따라 확인할 사항:** Claude Code 클라우드의 실제 브랜치 자동 생성 규칙, PR 대상 선택, GitHub 접근 권한, 사용 중인 계정·조직의 기능 설정.
- **예외:** 클라우드 테스트 환경에 필요한 의존성·외부 서비스·로컬 데이터가 없어 검증할 수 없을 경우, 이를 숨기지 말고 인계 문서에 기록한다. 보완 없는 상태를 '완료'로 표현하지 않는다.
- **인계가 목적:** 동기화 편의를 위해 소스코드나 설정을 억지로 동일하게 만들지 않는다. 차이를 **기록하고 검증해 통합**하는 것이 핵심이다.
